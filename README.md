# CertExpertsBot

`/check_portal` (также `/check-portal`) оценивает доступность и скорость https://techreg.gov.kz/.
Для меню Telegram используйте `/check_portal`: дефисы в именах команд меню не поддерживаются.
В группах поддерживается `/check_portal@имя_бота`.

Бот сразу сообщает о начале проверки. Итог содержит профиль доступа, результаты пяти
каскадов API, число успешных проверок, ошибки и пять самых медленных запросов.

## Что проверяется

Базовые ресурсы: `/index/`, `/constructor/player.js`, `/constructor/rest/apps/{appId}`,
`/Synergy/rest/translation/locales/`. `appId` извлекается из `data-app-id` текущей HTML-страницы;
конфигурация должна вернуть тот же ID. На 30.10.2026 портал переключился с 103 на 104.
Поддерживаются разные кавычки и пробелы в HTML. Проверяется содержимое ответа, а не только HTTP 200.

Загрузка кабинета:

1. При настройке учётной записи — `/Synergy/rest/api/person/auth?getGroups=true`.
2. Список услуг — `/Synergy/rest/api/registry/list?regGroupID=6d3169a2-dc30-4962-be32-2d1b88b1fa89`.
3. Два справочника, загружаемые кабинетом через `registry/data_ext`: `registry_portal_settings_registry_groups`
   и `registry_portal_settings_registries`. Запрашиваются те же поля названий, что использует интерфейс.

Список услуг проверяется как дерево групп/реестров, справочники — как согласованный JSON
со счётчиком и полями. Справочники измеряются и при ошибке списка услуг: это помогает
отличить зависание одного запроса от общей деградации. В этом случае весь каскад считается неуспешным.

При наличии учётной записи добавляется рабочий маршрут:
**Услуги → Оценка соответствия → Сервис подтверждения соответствия →
Сертификация соответствия продукции ЕАЭС → Сертификат соответствия продукции ЕАЭС**.

Это реестр `registry_certification_conformity_porducts_eaeu`, отличный от публичного
`certificates_reg_eaeu`. ID реестра и права берутся из авторизованного дерева услуг:
гостевой доступ для этого маршрута не используется.

Проверяется загрузка фильтров/прав реестров конечной группы (до восьми, сейчас четыре),
структуры выбранного реестра по `registryID`, определения формы `asforms/form_ext`
и первой страницы из 15 записей с видимыми колонками. Форма и колонки определяются
из актуальной структуры. Если у аккаунта нет основного права `rr_list`, выбирается
первый фильтр, как в интерфейсе; при собственном праве используется список без фильтра.
Пустой рабочий список допустим. Записи и заявки не создаются и не редактируются.

Каскад маршрута включает авторизацию/загрузку кабинета, фильтры выбранного реестра,
структуру, затем максимум загрузки списка и формы фильтров. Соседние реестры отображаются
интерфейсом независимо: их ошибки и задержки показываются как дополнительные замечания,
но не блокируют оценку выбранного маршрута. Без аккаунта маршрут явно помечается
как непроверенный с указанием нужных переменных окружения.

Для сертификатов РК (`certificates_reg_rk`), сертификатов ЕАЭС (`certificates_reg_eaeu`)
и деклараций ЕАЭС (`eaeu_production_conformity_declaration`) проверяются:

1. Фильтры — `registry/filters?registryCode=...`.
2. Структура реестра — `registry/info?code=...&locale=ru`.
3. Первая страница действующих документов — `registry/data_ext` с `filterCode=deistvuuschie`,
   `pageNumber=0`, `countInPart=20`.
4. Свойства и содержимое одного существующего документа из выборки —
   `api/docflow/doc/document_info?documentID=...` и `api/asforms/data/{dataUUID}`.

Проверяются структура записей, идентификаторы, совпадение свойств документа с выборкой,
наличие данных формы. Если выборка не прошла, неизвестные документы не запрашиваются.
Идентификаторы берутся из актуальной выдачи. Содержимое документов и данные участников
не включаются в отчёт и не сохраняются.

В конце независимо выполняются три поиска редкого значения `KZ.00000000.PROBE` через
`registry/data_ext` с теми же фильтром и размером страницы. Пустая выдача корректна при
`recordsCount=0` и `result=[]`; непустая также допустима, если структура и количество записей согласованы.

## Оценка каскадов и ограничения

Диагностика 28.10.2026 с авторизованным аккаунтом выявила: вход около 13 с,
два запроса списка услуг не завершились за 40 с каждый, полный список реестров также
не завершился за 40 с; справочники названий отвечали за 16–18 с. Поэтому быстрых
публичных выборок недостаточно для зелёного статуса.

Скорость каскада рассчитывается из длительности его шагов: последовательные шаги
суммируются, параллельные учитываются по максимуму. Это оценка API-последовательности,
а не замер времени появления интерфейса. Очередь запросов самого бота в длительность
запроса не включается. Браузерный кэш, отрисовка, все пользовательские права и весь
всплеск запросов меню не воспроизводятся. При неуспешном шаге каскад помечается незавершённым.

- Ошибка обязательного запроса/рабочего каскада означает красный статус с рекомендацией подождать.
- Обязательный запрос или рабочий каскад от 10 секунд — также красный статус.
- От 3 до 10 секунд — жёлтый статус с сообщением, что работать можно с задержками.
- Страница, скрипт, языки интерфейса, редкие тестовые поиски и права соседних реестров —
  дополнительные проверки: их сбой или задержка от 3 секунд дают жёлтый статус,
  а не объявляют отказ рабочих разделов. Ошибка получения конфигурации приложения
  остаётся критичной: без неё нельзя корректно проверить зависимые публичные API.
- Зелёный статус означает успешные быстрые обязательные проверки без замечаний
  по выполненным дополнительным проверкам. Покрытие гостевого/авторизованного профиля указано отдельно.

Пороги — эвристика, а не SLA портала. Измеряется API целиком, включая возможные серверные
кэши. Проверка не гарантирует работу ЭЦП, сохранения/отправки документов или самой СУБД.
Все запросы — GET к ресурсам чтения; создание, редактирование, активация и подписание не выполняются.

До 25 запросов с гостевым профилем; с текущим меню до 33 с учётной записью
(до 37, если последняя группа вырастет до восьми реестров). Одновременно выполняются
не более трёх запросов. Базовые ресурсы и шаги реестра имеют таймаут 10 секунд;
авторизация, список услуг, справочники кабинета и поиск — 25 секунд. Общий бюджет
проверки — 90 секунд. Его исчерпание возвращает неуспешный отчёт; остановка бота
отменяет запросы. Каждый ответ ограничен 8 МиБ после распаковки.

Результат общий для пользователей и кэшируется на минуту. Одновременные команды используют
один результат. Автоматических повторов тяжёлых запросов нет.

## Настройка аккаунта в appsettings.json

Рабочий бот читает настройки из `appsettings.json` рядом с `CertExpertsBot.dll`
(через `AppContext.BaseDirectory`), раздел `PortalHealth`:

```json
{
  "PortalHealth": {
    "AccountLogin": "логин аккаунта портала",
    "AccountPassword": "пароль аккаунта портала"
  }
}
```

Добавляйте раздел к существующим настройкам, сохраняя `ConnectionStrings` и остальные
параметры. Переданные пользователем данные уже добавлены в локальный
`CertExpertsBot/appsettings.json`. Файл исключён из Git и явно копируется при сборке
и публикации. На Linux нужно передать обновлённый файл вместе с публикацией и
перезапустить бот: сервис читает настройки при первом использовании.

В рабочем боте профиль учётной записи обязателен. Отсутствующий/неполный раздел
`PortalHealth` — критичная ошибка конфигурации в отчёте, а не повод незаметно
переключиться на гостевой профиль. При корректном файле маршрут ЕАЭС выполняется
под заданным аккаунтом. Настройка через переменные окружения больше не используется.

Учётная запись используется для авторизации, начальной загрузки кабинета и рабочего
маршрута сертификации ЕАЭС. Публичные документы и поиск продолжают проверяться
под гостевым доступом из актуальной конфигурации портала. Пароли не выводятся
в ответы, логи или диагностические сообщения.

## Проверка изменений

Сборка: `dotnet build CertExpertsBot/CertExpertsBot.csproj`.

Регрессионные проверки без запросов к порталу и сторонних тестовых пакетов:
`dotnet run --project tests/PortalHealthChecks/PortalHealthChecks.csproj`.
Покрываются кэш, параллелизм, схемы ответов, изоляция профилей, оценка каскадов,
лимит времени, отмена, восстановление и длина сообщения Telegram.

Ручной замер портала с настройками из файла:
`dotnet run --project tests/PortalHealthChecks/PortalHealthChecks.csproj -- --live --settings CertExpertsBot/appsettings.json`.

## Мгновенный ответ и нули на Linux

Если независимые базовые запросы завершаются ошибкой соединения за доли секунды,
конфигурация приложения и гостевой доступ не получены. Зависимые проверки кабинета
и документов при этом пропускаются. Это не означает быстрый ответ API портала.

Отчёт различает HTTP-попытки и пропущенные проверки, показывает DNS/TLS/соединение/
прокси отдельно, отображает короткие измерения в миллисекундах. Пропущенные каскады
помечаются «не проверен». У результата из кэша указан возраст; повторных запросов
в течение минуты может не быть, в том числе после сетевой ошибки.

Для диагностики запускайте команды в том же окружении, что и бот. Если бот работает
в контейнере, проверять нужно из контейнера, а не только с хоста:

```sh
getent ahosts techreg.gov.kz
curl -sS -o /dev/null --connect-timeout 10 --max-time 20 \
  -w 'HTTP=%{http_code} total=%{time_total}s\n' https://techreg.gov.kz/index/
```

Ошибка `getent`/curl о разрешении имени указывает на DNS; ошибка curl о сертификате
или согласовании TLS уточняет причину защищённого соединения; отказ или таймаут
соединения требует проверки маршрута, исходящего HTTPS и прокси. Точный диагноз
нужно делать по коду ошибки из окружения сервера, а не по доступности сайта с другой машины.
